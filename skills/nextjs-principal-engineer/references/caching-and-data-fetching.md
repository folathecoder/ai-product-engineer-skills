# Next.js Caching & Data Fetching Mastery

> **Purpose**: Authoritative reference for the Next.js 16+ Cache Components paradigm, Partial Prerendering (PPR), `'use cache'`, tag-based revalidation, and zero-waterfall data fetching patterns.

---

## 1. The Cache Components Mental Model (Next.js 16+)

Next.js 16 fundamentally replaced implicit caching with **explicit, opt-in caching** centered around **Cache Components**:

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

### Core Axioms
1. **`fetch()` is UNCACHED by default**: Calling `fetch('https://...')` runs dynamically at request time unless wrapped in `'use cache'` or configured explicitly.
2. **Dynamic execution is the default**: Pages, layouts, and Route Handlers execute at request time unless their inputs and data sources are pure or explicitly cached.
3. **Partial Prerendering (PPR) is the engine**: Build time produces a **static shell** containing cached outputs and `<Suspense>` skeletons. Uncached data streams into `<Suspense>` boundaries at request time.
4. **Cache by function, not route**: Apply `'use cache'` to granular async functions rather than toggling route-wide dynamic flags.

## 2. The `'use cache'` Directive & Scopes

The `'use cache'` directive can be placed at the file, component, or function level. **All cached targets must be `async`.**

### Scope Variants

| Directive | Cache Location | Use Case |
|---|---|---|
| `'use cache'` | Server in-memory LRU + Static Shell participation | Default for shared, public data (e.g. blog posts, product catalog). |
| `'use cache: remote'` | Durable shared store via `cacheHandlers` (Redis/KV) | High-traffic serverless applications needing multi-instance cache persistence. |
| `'use cache: private'` | **Client browser cache only** | Enables personal data (reading `cookies()`/`headers()`) to participate in client prefetches. |

### Canonical Cached Function Pattern

```tsx
// src/data/products.ts
import 'server-only'
import { cacheLife, cacheTag } from 'next/cache'
import { db } from '@/lib/db'

export async function getFeaturedProducts(category: string) {
  'use cache'
  cacheLife('hours')
  cacheTag('products', `category-${category}`)

  return await db.products.findMany({
    where: { category, isFeatured: true },
  })
}
```

### Critical Rules & Constraints for `'use cache'`
- 🚫 **No Runtime APIs Inside Cache Scopes**: Calling `cookies()`, `headers()`, or `searchParams` inside a `'use cache'` scope throws `next-request-in-use-cache`.
  - *Fix*: Read runtime APIs **outside** the cached function and pass the required values as arguments.
- 🚫 **Non-Serializable Arguments**: Cache keys are generated by hashing function identifiers and serialized arguments. Arguments must be serializable (primitives, plain objects, arrays, Dates).
- 🚫 **Pass-Through Slot Pattern**: JSX children passed to a cached component are treated as pass-through and are not introspected, enabling dynamic slots inside cached wrappers:
  ```tsx
  export async function CachedCardWrapper({ children }: { children: React.ReactNode }) {
    'use cache'
    return <div className="card-shell">{children}</div>
  }
  ```

## 3. `cacheLife` Profiles & Configuration

`cacheLife` defines three distinct lifecycle phases for any cached entry:
- **stale**: How long client browsers may serve the cached data before checking the server (minimum client stale is 30s).
- **revalidate**: Background refresh interval on the server (SWR).
- **expire**: Hard expiration after which cached data is purged.

### Built-in Profiles Reference

| Profile Name | `stale` | `revalidate` | `expire` | Typical Use Case |
|---|---|---|---|---|
| `'seconds'` | 30s | 1s | 1m | Real-time dashboards, live stock counters |
| `'minutes'` | 5m | 1m | 1h | News feeds, active community forums |
| `'hours'` | 5m | 1h | 1d | Product catalogs, store prices |
| `'days'` | 5m | 1d | 1w | Blog articles, marketing pages |
| `'weeks'` | 5m | 1w | 1m | Documentation, changelogs |
| `'max'` | 5m | 1m | 1y | Static assets, immutable legal notices |
| `'default'` | 5m | 15m | 1d | General server-side cached queries |

## 4. Cache Invalidation Matrix: `updateTag` vs. `revalidateTag` vs. `refresh`

Next.js 16 provides three distinct invalidation APIs:

```
                          ┌─────────────────────────────┐
                          │ Need to invalidate cache?   │
                          └──────────────┬──────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
         Inside Server Action?                          Outside Server Action?
                 │                                      (Route Handler / Webhook)
        ┌────────┴────────┐                                      │
        ▼                 ▼                                      ▼
 User needs immediate   Background SWR                     Background SWR
 read-your-writes?       is acceptable?                    is acceptable?
        │                 │                                      │
        ▼                 ▼                                      ▼
  `updateTag(tag)`  `revalidateTag(tag, 'max')`         `revalidateTag(tag, 'max')`
```

### 1. `updateTag(tag)` — Immediate Read-Your-Writes
- **Context**: Allowed **only** inside Server Actions.
- **Behavior**: Purges the cache immediately and re-fetches within the same server request pass.
- **Use Case**: User submits a form changing their profile or creating an item, expecting to see it instantly upon response.
```ts
'use server'
import { updateTag } from 'next/cache'

export async function editTitle(id: string, newTitle: string) {
  await db.posts.update({ where: { id }, data: { title: newTitle } })
  updateTag(`post-${id}`)
}
```

### 2. `revalidateTag(tag, profile)` — Background SWR
- **Context**: Usable anywhere on the server (Webhooks, Route Handlers, cron jobs, Actions).
- **Requirement**: **Requires a `cacheLife` profile as second argument** (e.g. `'max'`). The legacy single-arg form is deprecated.
- **Behavior**: Marks the cache as stale. Readers continue receiving cached data until background revalidation completes.
```ts
// Webhook handler
import { revalidateTag } from 'next/cache'

export async function POST(req: Request) {
  // Stripe webhook event
  revalidateTag('subscription-plans', 'max')
  return Response.json({ received: true })
}
```

### 3. `refresh()` — Uncached UI Sync
- **Context**: Allowed inside Server Actions.
- **Behavior**: Instructs the client router to re-fetch and re-render uncached components on the current page without invalidating any cached tags.
- **Use Case**: Updating an uncached badge count or dynamic notification indicator after an action.

## 5. Zero-Waterfall Data Fetching Architecture

### Anti-Pattern: Sequential Waterfall
```tsx
// ❌ ANTI-PATTERN: Sequential awaits cause network waterfall
export default async function DashboardPage() {
  const user = await getUser()         // 200ms
  const stats = await getStats()       // 300ms (waits for user)
  const feed = await getFeed()         // 400ms (waits for stats)
  // Total blocking time: 900ms!
  return <Dashboard user={user} stats={stats} feed={feed} />
}
```

### Idiomatic Pattern A: Parallel Data Fetching
```tsx
// ✅ IDIOMATIC: Parallel fetching executes concurrently
export default async function DashboardPage() {
  const [user, stats, feed] = await Promise.all([
    getUser(),
    getStats(),
    getFeed(),
  ])
  // Total blocking time: ~400ms (longest request)
  return <Dashboard user={user} stats={stats} feed={feed} />
}
```

### Idiomatic Pattern B: Component-Level Streaming (Best User Experience)
Push data fetching into independent Server Components wrapped in `<Suspense>` so the page shell renders instantly and sections stream in as they resolve:

```tsx
// ✅ OPTIMAL: Streaming Suspense eliminates page blocking
import { Suspense } from 'react'
import { UserHeader, UserSkeleton } from './UserHeader'
import { StatsCards, StatsSkeleton } from './StatsCards'
import { ActivityFeed, FeedSkeleton } from './ActivityFeed'

export default function DashboardPage() {
  return (
    <div className="dashboard-grid">
      <Suspense fallback={<UserSkeleton />}>
        <UserHeader />
      </Suspense>

      <Suspense fallback={<StatsSkeleton />}>
        <StatsCards />
      </Suspense>

      <Suspense fallback={<FeedSkeleton />}>
        <ActivityFeed />
      </Suspense>
    </div>
  )
}
```
